**P01, invite-only sign-up.** The backend already does this (`POST auth/password`, `auth/password/forgot`, `auth/password/reset`, `auth/invite/accept` in `config/routes.rb:45-48`, with `UserInvitation` single-use 7-day digests), so this plan has no endpoint work. It deletes every "Create account" path, the A3 role picker and the typed `TMN-…` invite codes from the storyboard (`plan/storyboard/refined/_src/gen.py`) and from guides 00/01/02. It adds A8 Set password (from `tamanly://invite/<t>`), A2b Forgot and A2c New password, and makes deep links work while signed out. Someone signed in with no modes lands on `/invites` with an empty state.

**P02, visitor categories.** A new org-owned `visitor_categories` table (`name`, `base` ∈ `guest delivery ehailing service contractor`, `active`, `position`) and a nullable `visitor_entries.visitor_category_id`. `visit_type` stays the system enum and is written from `base`, so the gate, onsite board and guard filters don't change. `VisitorPasses::Create` takes `category_id` instead of `kind`. Adds `GET /api/v1/visitor_categories`, a `category {id,name}` field on the pass serializer, an admin CRUD page (ported from the market-policy table), seeds the five defaults per org (Contractor included), and rewrites the guide 04 C2 chips.

**P03, booking limit per week or month.** Renames `facilities.per_month` to `booking_limit` and adds `booking_limit_period` (`week`|`month`, default `month`). A single `Bookings::Quota` helper (KL calendar week starting Monday, or calendar month) is used by both `Bookings::Create` and `FacilitySerializer.detail`, which now returns `booking_limit`, `booking_limit_period` and `quota{used,limit,period,resets_on}` and drops `per_month`. The admin Booking rules page gets a count + Week/Month select. Guide 09 bullets are listed.

**P04, one app, guard view by role.** No guard APK. `me.modes` decides the shell: guard → `/guard`, resident → `/home`, both → guard by default with a switch on G1, staff-only → a static `/console` page. Guard calls send `X-Taman-Id` and drop `X-Unit-Id`. The only backend change is `Walkins::Request`: `POST guard/walkins` notifies the host, and the serializer exposes `visitor_pass_id`. Adds W1 Walk-in and W2 Delivery screens (unit search, 3 s polling). Shift notes and incidents stay console-only.

**P05, backend gaps.** Seven new routes in three modules. **A11 (guard):** `GET guard/permits/:id`, `POST guard/permits/:id/deny` (writes a denied gate row, not a permit status), `GET guard/gate_events/csv`. **A12 (resident billing/permits):** `GET billing/statement/pdf` (reuses `Finance::ArAging.detail` + `ArAgingStatementPdf`), `POST access_requests` (a notification to the host, no table), `PATCH permits/:id` (refund account, number encrypted, API returns only `number_last4`). **A13:** `POST incidents` (resident, via `Gate::ReportIncident`), and listing `photos[]` on the existing create/update. One migration (permit refund columns).

## Out of scope (explicit)

- **SMS / phone OTP** anywhere: no code, copy, columns or `phone_unverified` (README decision 1).
- **Firebase Auth sign-up/sign-in**: `POST /auth/firebase` is not built and `firebase_auth` is removed. `firebase_core` + FCM push stay.
- **Self sign-up** and typed invite codes: no signup route, no `GET /invites?code=`, no app "resend invite" (admins resend from the console).
- **A separate guard app/APK/flavor**: one bundle, with the guard view picked by role. No staff mobile UI, no guard shift notes/incidents in the app, no offline gate mode.
- **`POST /uploads`**: files go multipart on the owning route (permits, listing `photos[]`).
- Also not planned: per-taman visitor category visibility, org-wide booking limit, an access-request inbox table, incident photos, Google/Apple sign-in.
